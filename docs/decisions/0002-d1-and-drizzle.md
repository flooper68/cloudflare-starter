# 0002. Cloudflare D1 with Drizzle as the database

- Status: Accepted
- Date: 2026-10-28

## Context

The starter needs a relational store for app data and for auth (users, sessions, accounts, OAuth clients). It runs entirely on Cloudflare Workers and should run locally with no service to install. A new project should get a working database without provisioning a server or a third-party account.

## Decision

We use Cloudflare D1 (SQLite) through the `DB` binding, one database per environment, with Drizzle ORM for the schema and queries. Migrations are SQL files generated by `drizzle-kit generate` into `packages/features/migrations/` and applied by Wrangler (`wrangler d1 migrations apply`), locally and remotely. `drizzle-kit push` is never used against a remote database. Migrations are additive; destructive changes ship separately once no deployed code depends on the old shape.

## Consequences

Positive:

- No database server, connection pooling or credentials: the binding is the permission.
- Local development uses Wrangler's local D1; CI applies migrations to an empty D1 with no account.
- Drizzle gives typed queries and a schema that Better Auth's adapter shares.

Negative:

- D1 has no interactive transactions; Better Auth's adapter runs with `transaction: false`, and multi-statement atomicity needs `batch()`.
- SQLite limits: per-database size cap, single-writer throughput, fewer column types.
- Schema changes that SQLite cannot alter in place need table rebuilds in generated SQL.

## Alternatives considered

- **Postgres via Hyperdrive (Neon or another host).** Full Postgres features and transactions, but adds an external provider, credentials, a server to provision and a network hop; local dev needs a running Postgres. Too much for a starter. Rejected.
