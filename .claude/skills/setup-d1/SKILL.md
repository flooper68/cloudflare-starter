# D1 database

The web Worker's only database is D1 (`DB` binding), one database per environment, named in `apps/web/wrangler.jsonc`. Schema is Drizzle in `packages/features/src/db/schema/`; migrations are SQL in `packages/features/migrations/`, generated by drizzle-kit and applied by Wrangler. Full guide: `docs/guides/how-to-setup-d1.md`.

## Local

1. `bun run db:migrate:local`
2. `bun run doctor` should show "local D1 migrations applied".

Nothing else: Wrangler keeps the local database under `apps/web/.wrangler/state`.

## Remote (first time)

1. Check the user is logged in: `bunx wrangler whoami` (run in `apps/web`). If not, ask them to run `bunx wrangler login`; do not handle tokens yourself.
2. Ask whether data must stay in a region. If yes, use `--jurisdiction eu` (fixed at creation).
3. Preview, then create: `bun run setup:cloudflare --env <env> --dry-run`, then without `--dry-run`. It creates D1, R2 and queues and writes the D1 id into `wrangler.jsonc`. Creating resources changes the user's account: confirm before the real run.
4. Apply migrations: `cd apps/web && bunx wrangler d1 migrations apply DB --remote --env <env>` (no `--env` for develop).

## Changing the schema

1. Edit the Drizzle schema. Never hand-edit `schema/auth.ts`: it is generated (see the setup-auth skill).
2. `bun run db:generate`, then read the generated SQL.
3. `bun run db:migrate:local`, run the app or tests.
4. Commit the `.sql` file and `migrations/meta/` together. CI fails if the schema and migrations disagree.

Rules: additive first (new tables, nullable or defaulted columns); renames and type changes go through a new column, a backfill and a later drop; never `drizzle-kit push` against a remote database. Migrate before deploying the code that needs it.

## Verify

`bun run verify`, `bun run doctor`, and for remote: `bunx wrangler d1 migrations list DB --remote --env <env>` shows nothing pending.
